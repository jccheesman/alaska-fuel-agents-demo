What can a team of AI agents do with a fuel-supply network, and how do we find out?

This page walks through one research harness: real data about how fuel reaches Alaska's communities, a set of tools agents may call, five written skills, four ways of organizing an agent team, and a storm that closes the Port of Nome halfway through the job. The map in the middle shows the deliveries before the storm, the moment the plan breaks, the correct reroute, and what the agents actually produced.

Start here: six words you will meet

Agent

A language model given a goal, a set of tools and a loop: it reads, decides to call a tool, reads the result, and repeats until it submits something. Here the goal is a fuel-delivery plan and the tools answer questions about a network database.

Harness

Everything around the model that makes the work auditable and fair. It decides what data an agent may see and when (layers L1, L2, L3), logs every tool call with a receipt id, refuses reports with invented ids or unbacked citations, freezes every file an agent sees, and scores the result the same way for every team.

Skill

A short written procedure, a SKILL.md file, that tells an agent how to do one job well: orient in the data, plan routes, revise under a disruption, reassess with late context, build and submit the report. Skills are shown only when their tools and data layer are available.

Tool

A function the agent can call by name with arguments. There are 29: a handful to look things up and route, a dozen to build the report piece by piece, two for the disruption, three for the context documents. Every call returns a receipt (r-0042) that a claim can cite.

MCP server

The Model Context Protocol is a standard way to offer tools to any agent framework. The harness serves exactly the same tools over MCP (standard input and output, one process) as it does in-process, and a test asserts the two lists are byte-identical.

OKF concept map

The network as linked, versioned text pages (the Open Knowledge Format layer): a start page, an ontology, one page per region, hub, corridor and month, each stamped with the database hash it was built from. An agent reads one page per call and can copy its ids verbatim.

The five skills, as the agents read them

Each card's header is the skill's own front matter. Open one to read the full procedure.

The tools, grouped by what they do

Descriptions are the tool docstrings, the same text every framework hands the model. The badge on each tool is the data layer that unlocks it (L1 the network, L2 the disruption, L3 the context documents); a tool outside the run's current layers answers exactly like a tool that does not exist.

Four ways to organize the same agents

  
Every team gets the same task text, the same tools, the same skills, the same models and the same budgets. Only the shape of the team differs, and the one paragraph that tells each agent where it sits. The study asks whether that shape changes what gets planned.

The life of a run

  
One run is one team working one task through three checkpoints. The harness releases information in layers, the way it arrives in real planning: the network first, then a disruption, then the slower socio-economic context.

      Try it yourself
      
  
      Three Colab notebooks, no virtual machine needed. The first two need no language model at all.
      
  
      
    
      
      
      1 · DuckDB on the real network
      
      
      Open fuel_network.duckdb directly: tables, the passable_edges macro and views, routing with the duckrouting extension (Anchorage → Nome before and after the closure), graph analytics with Onager, H3 tiles, the spatial extension, DuckPGQ and full-text search.
      
      
      Open in Colab view source
      
    
      
    
      
      
      2 · Call the agents' tools
      
      
      List the MCP surface, call describe, resolve("Nome"), route, deliver the D2 notice yourself and watch check_disruption_impact appear. Every call leaves a receipt in tool_log.jsonl, exactly as it does for an agent.
      
      
      Open in Colab view source
      
    
      
    
      
      
      3 · Run the linear team with an open model
      
      
      On a free GPU runtime: install Ollama, pull an open-weight model, and run the lin chain through plan, disruption and reassessment. Download the run folder and the build script adds it to this map as "your run".
      
      
      Open in Colab view source
      
    
      
  
      
  
      The harness repository is private while the study is under way, so the notebooks read a fine-grained, read-only GitHub token from Colab's Secrets panel (name it GH_TOKEN). Nothing is written back.
      
  
      How to read a receipt
      
  
      {"ts": "2026-10-22T19:41:08+00:00", "tool": "route", "layer": "L1",
 "args": {"hubs": ["hub:h000698", "hub:h000493"], "month": 9}, "args_sha256": "84ef…",
 "agent_label": "stage-2", "checkpoint": "plan", "bytes_returned": 1812,
 "r_ids": ["r-0037"], "error": null, "result_sha256": "28c0…", "result_path": "tool_results/r-0037.json"}
      
  
      One line of tool_log.jsonl, lightly abbreviated. The full result sits under tool_results/r-0037.json. A claim in the report that says cites: ["r-0037"] is checked against exactly this line: the scorer asks whether the run ever received it, and the judge asks whether it supports the sentence.
